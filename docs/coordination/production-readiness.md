## 上线顺序和验收责任

1. **运维确定不可变的发布身份与代理拓扑。** 账号 issuer 与管理员域名分开，核对 DNS（含 AAAA）、可从客户端和外部 RP 验证的证书、时钟、固定回调及登录入口。只暴露 edge；检查 `/internal/metrics`、数据库、Valkey 不从外部可达；如果前置 CDN/负载均衡，确认 Go 只采信预期代理生成的客户端 IP，两个不同来源不会被合并到同一限流桶，外部伪造头无效。正式端口与证书不使用内部 CA 或 `--insecure`。
2. **运维执行首装，前后端一起验收首位管理员。** 在限制访问的最终入口上，用真实 TLS SMTP 向专用邮箱完成首装邀请码、注册验证和密码恢复；提升该账号后，从管理台走中央同意、回跳、绑定 TOTP、保存单次恢复码并进应用审核。用专用账号验证错误/重复校验、MFA 前后管理接口的权限差异和会话隔离。不要把 CLI 发码或页面 200 当作首装完成；若 SMTP 不能送达，先修投递，不开放注册绕过。凭据只经私密渠道交付。
3. **前端与 RP 接入方验收真实 OAuth。** 校验两个 Discovery 和 JWKS 的公开 URL、issuer 与签名配置。用独立 Web RP（首发若包含 Game Info，须用其实际部署）验证授权、拒绝、回跳、换码、应用会话、刷新/撤销及中央退出和应用自己的退出；再验测试成员、审核发布、旧批准配置保持生效、暂停后拒绝。Game Info 的隔离协议夹具记录见 [提取交接](game-info-ui-extraction.md)，不等同实际跨站首发。浏览器侧检查 `Location`、`Set-Cookie` 的安全属性和归属、不同站点会话、深链接、直接刷新、身份响应头、404/静态资源/图标、多语和移动端；保留脱敏证据。
4. **运维先落地备份和观测，再开放。** 在实际机器配数据库与独立根密钥两份异地加密备份、明确负责人、调度/失败告警、保留期和恢复时间目标；用实际配置验证可解密及新库恢复，保留上个可用版本和切回条件。实际部署没有预装监控；至少建立双站外部 HTTPS 探测及 API、邮件失败/积压观察。`account` 和 `edge` 镜像没有 Docker healthcheck，`compose up --wait` 对它们不证明真实 HTTP 可用；以外部页面、回调及 API 探测作为放流判据。见 [Compose `up --wait`](https://docs.docker.com/reference/cli/docker/compose/up)、[恢复](../run-backup-recovery.md) 与 [观测](../run-observability.md)。

任何 P0 未关闭，不开放公网注册和真实 OAuth 流量。若受控验收失败，保留证据并停止切流；发生持久数据变化时按恢复指南评估回退，而不是直接降镜像或重新初始化密钥。
