# 性能、容量与资源验收

状态：用户要求纳入性能考虑；本文件为测量与设计约束草案，没有运行基准或确定生产 SLO。获实施授权后再创建工具与执行测试。

## 测量原则

性能必须与正确性、安全、硬件成本和真实负载一起评价。路由或 ORM 的单项跑分不能代表登录服务吞吐；类型安全、代码生成和使用 Go 也不证明尾延迟达标。

将浏览器端到端耗时、应用内部耗时、数据库等待、密码/密钥计算和外部供应商耗时分开记录。既报告包含外部依赖的用户体验，也报告受控依赖下可复现的系统性能。

## 已知规模与分阶段验证

用户补充：当前生态预计低流量，未来可能为类 pixiv 社区，活跃用户最多双位数；生产硬件未定。这是业务预期，不是明确统计口径的 DAU 或峰值并发，不能直接换算登录 RPS。总注册用户、历史授权记录和自动刷新请求也不能由活跃用户数直接推断。

据此调整首期工程建议：优先单机、小连接池、有界任务和低空闲资源开销；暂不需要为未知高流量建立集群、分片或跨机缓存。长期模块边界、身份安全、事务和迁移要求保持，后续通过测量决定扩容。

验证按阶段执行，避免把完整大规模压测平台变成首期开发前置：

1. 原型阶段验证协议、事务与实际 SQL，记录基本延迟和空闲/短时负载资源。
2. 发布前在最终选定硬件上验证关键完整流程、合理小规模并发、短时突发、重启和依赖失败，确定初期容量与预算。
3. 有真实流量后记录观测基线；只有排队、资源饱和、增长或容量目标变化才增加长时/高负载测试与架构复杂度。

下面完整场景清单作为按风险选取的目录，不要求每次修改运行全量性能测试。单次消费、并发刷新、限流和故障恢复仍需测试；低活跃不意味着不会有自动重试或恶意流量。

## 仍需确定的负载与预算

| 输入 | 当前状态 | 用途 |
| --- | --- | --- |
| 生产 CPU、内存、磁盘与资源上限 | 用户明确暂未确定；部署准备时再选定 | 设置进程与连接预算 |
| 生态活跃规模 | 用户预计最多双位数，未定义 DAU/同时在线统计口径 | 采用低流量、低空闲开销的首期方案 |
| 账号数、应用数、授权记录和会话保有量 | 待确认 | 数据基数与索引验证 |
| 稳态与峰值登录、授权、刷新、API 验证请求率 | 待确认；在线人数不直接换算 RPS | 场景权重、突发与排队 |
| 浏览器设备和网络档位 | 待确认 | 首屏、交互和资源预算 |
| 可接受 p95/p99、错误率、恢复时间与成本 | 待确认 | 上线门槛与容量余量 |

这些参数缺失时可以规划测量方法，不能声称通过性能验收。测试前记录临时假设；正式上线前将目标数值、测量窗口和验收条件定案，不套用他人 QPS。

无需为了继续文档评审立即购买服务器或估计精确 QPS；硬件和初期数值目标在实际部署准备时落实。

## 需要分别测量的场景

| 场景 | 重点与区分 |
| --- | --- |
| 密码登录/注册 | Argon2id CPU/内存与并发上限、失败请求和限流成本 |
| 已登录授权 | SSO、同意、应用已批准配置读取，避免每步多次重复查询 |
| 授权码兑换 | 单次消费、客户端认证、签名与持久化事务 |
| 刷新 | 正常、过期、并发竞争、重放及客户端认证成本 |
| 外部 JWT 验证（若确认） | 本地公钥缓存命中、未知 kid、冷启动与轮换；分别测普通/敏感接口 |
| Go Web 会话 | 缓存/数据库读取、失效与权限提升；不能借长期缓存忽略撤销 |
| 后台列表与审核 | 真实数据基数、分页、排序、筛选与配置生效并发 |
| 邮件/outbox | 用户响应与后台投递延迟分别测量，验证积压恢复和去重 |
| 前端 | 登录首屏、表单可交互、授权确认、控制台长列表、两个主题/语言 |

令牌签名、密码校验与客户端 secret 校验成本不同。不能用纯会话读取负载冒充密码登录吞吐。第三方登录不在压力测试中直接冲击供应商，受控替身与专属真实测试 client 分别验证。

## 热路径与资源上界

- Ent 查询选择必要字段，避免无界 edges/preload 和 N+1。以实际 SQL、查询计数、扫描行、计划与锁等待判断；关键事务允许适配层使用受控 SQL。
- PostgreSQL 连接池按各 API/worker 实例合计预算，保留迁移与运维余量；增加应用副本不能无界增加总连接。外部调用不占用数据库事务。
- 令牌和 Web 会话的状态检查按安全要求设计；减少冗余往返不等于省略当前授权校验。并发刷新不能通过去掉锁或事务获得更高跑分。
- 密码哈希使用有界并发和队列/拒绝策略，避免突发耗尽内存；候选 Argon2id 参数以目标硬件测试，不为提高吞吐降低已确定安全基线。官方参数能力见 [Go argon2](https://pkg.go.dev/golang.org/x/crypto/argon2)。
- 签名密钥和 JWKS 正确缓存与轮换；未知 kid 触发的刷新必须有并发合并与频率控制，不能每个恶意 token 发起外部请求。
- 缓存限制连接、payload、键数量和 TTL，验证热点、驱逐、重连与故障行为；缓存产品未定，不依赖未验证的专属功能。
- outbox 有索引、批量领取、租约、有限并发和清理策略；积压恢复不允许抢占全部 API 数据库连接。
- 日志避免原始请求体与高频成功事件刷屏；追踪采样、导出队列和背压有上界。遥测故障不可阻塞正常业务，但关键审计的失败策略必须单独设计。采样概念见 [OpenTelemetry](https://opentelemetry.io/docs/concepts/sampling/)。

## 前端与部署成本

按 [全栈复核](stack-review.md) 评估 account SSR、admin CSR、developer 公开内容预渲染/控制台 CSR。比较首屏 JS、LCP/INP/CLS、交互响应和服务器 CPU/RSS；渲染建议尚未确认或实测。

按需加载图标、插画、复杂控件与表格；列表分页，达到实际需要时再引入虚拟化。Storybook 只在开发/CI 构建，不随生产应用加载。共享包的 tree-shaking 和 Tailwind 扫描需检查真实产物，不只看配置。

用户站与管理台可以独立构建与部署；仅使用静态/CSR 能力的应用不强制常驻 SSR 进程。测试两应用、Go、worker、数据库与缓存合计资源，不只报告 API 单进程内存。

## 实施后测试方法

1. 固定版本、数据集、构建模式、硬件、容器资源、网络和哈希参数，记录场景权重；负载机与被测服务分离，避免负载机先饱和。
2. 区分冷启动、预热后稳态、逐级加压、突发和持续运行；记录客户端实际发起与完成速率，避免闭环等待掩盖排队。
3. 同时记录吞吐、p50/p95/p99、超时、错误与拒绝率、CPU、RSS/分配、GC、池等待、SQL/缓存延迟和任务积压。不能删除超时请求再计算漂亮分位数。
4. 在负载中验证并发单次消费、授权隔离和失败回滚；成功条件包含正确性，不能只看 HTTP 200。
5. 测依赖变慢/不可用、重启、密钥轮换和 worker 积压，观察恢复、背压及撤销窗口。
6. 对回归使用相同方法复现和定位；初期建立基线后确定允许变化预算。失败时给出差异、证据和修复，不反复跑到偶然通过。

小规模测量记录样本量与波动；样本不足时报告原始分布或最大值及限制，不从少量请求的 p99 推出精确容量结论。

负载工具候选在实施时结合许可证、CI 与 Windows 确定，本轮不安装。Go CPU/内存/阻塞与追踪诊断参考 [Go diagnostics](https://go.dev/doc/diagnostics)；数据库计划参考 [PostgreSQL EXPLAIN](https://www.postgresql.org/docs/current/using-explain.html)。带执行的计划可能实际修改数据，应只对专属测试资源运行。

## 交付与门槛

未来报告应包含可复现方法、硬件成本、数据基数、请求混合、全部关键指标、饱和点、余量、错误和正确性结果。原始结果不得含真实账号或秘密。

原型阶段证明兼容和瓶颈，产品阶段证明端到端体验，发布阶段在目标环境证明容量与故障恢复。未确定负载/SLO、未执行测试或仍有并发正确性缺陷时，不能宣称“性能足够商业使用”。
