# 全栈长期工程与性能复核

日期：2026-10-17。状态：资料复核与工程建议，未安装依赖、运行原型或测得性能。用户已确认的方向仍有效，新增建议不自动成为用户决定。

## 结论

保留 Nuxt/Vue、Headless + Storybook、Go 模块化单体，以及 Ent 的文档基线。chi、Fosite、Huma 保留候选，但验证风险不同：Fosite 的生产持久化和身份产品整合是重点，不能只检查能否签发一个 token。

建议调整前端渲染分配、缓存产品评估和性能验收方式。当前按 ADR-0017 合并为用户站＋管理台；两应用不等于两个常驻 SSR Node 进程，也不等于所有私人页面都应服务端渲染。没有业务负载和目标硬件数据，不能宣称当前框架组合满足某个 QPS 或商业 SLA。

用户随后说明生态预计低流量、活跃用户最多双位数，硬件未定。首期建议优先低空闲成本与简单单机运行，保留已确认框架和安全设计；不为此规模规划分片、Kubernetes、独立消息平台或必需的全套追踪服务。性能方法按 [performance.md](performance.md) 分阶段执行。

## 分项判断

| 部分 | 长期判断 | 性能关注 | 本轮结论 |
| --- | --- | --- | --- |
| Nuxt/Vue | 单一前端体系便于共享；需要稳定升级与 SSR 数据隔离 | 水合、首屏 JS、SSR 进程内存、重复请求 | 保留；按应用/页面选择渲染方式 |
| Reka/Tailwind | 原语与语义 token 适合品牌迭代；需维护封装 | 原语导入、弹层、CSS 扫描、长表格 | 继续推荐候选；按需组合，不封装全库 |
| Storybook | 组件契约、状态与可访问性回归工具 | 开发/CI 构建成本 | 保留；不进入生产运行依赖 |
| Go 模块化单体 | 减少网络边界，便于事务与逐步拆分 | CPU、GC、数据库等待、任务竞争 | 保留；API 与 worker 是否分进程仍验证 |
| chi/net/http | 标准 HTTP 组合与适配成本清晰 | 中间件、分配与请求体成本 | 继续推荐，不能以路由微基准承诺整站速度 |
| Huma | 业务契约和输入验证集中，支持类型生成 | 大请求验证、序列化、反射与额外中间件 | 仅业务 API；实测额外成本，不接管协议响应 |
| Fosite | 减少自写协议；生产存储与产品能力仍由项目负责 | client 认证、令牌存储、锁与刷新并发 | 保留候选，设独立集成门槛 |
| Ent | 显式 schema 与生成 API 利于演进，需维护代码生成 | SQL 数量、关联加载、锁与事务边界 | 已确认基线；禁止默认加载全图 |
| PostgreSQL | 适合权威状态和事务，备份迁移能力需落地 | 连接池、索引、膨胀、清理、慢查询 | 继续推荐；不先引入分库和读写分离 |
| SQL 迁移/Goose | 可审查、可重放，独立于 ORM | DDL 锁、回填、发布停顿 | SQL 迁移已确认，Goose 优先验证 |
| 缓存 | 会话、状态与限流用途不同；发行物许可需明确 | 网络往返、TTL、驱逐、连接与热点 | 加入 Valkey 比较，尚未替换或选定 |
| outbox/worker | 可靠投递易审计，无需首期消息平台 | 轮询、批量领取、积压与表清理 | 继续推荐；邮件不在请求事务中发送 |
| slog/OpenTelemetry | 有助于定位回归与运营事件 | 日志量、标签基数、采样及导出背压 | 日志保留建议，追踪按预算采样 |
| Compose | 与初期单机运维匹配，可控但非高可用承诺 | 容器资源预算、IO、SSR 数量 | 保留方向，不为商业化预设 Kubernetes |

表格是工程判断；官方能力依据如下，未基于跨框架统一实测排名。

## 前端渲染建议

Nuxt 支持通用、客户端和混合渲染；Next 提供 Server/Client Components。两者均可构建长期项目，现有需求没有证据证明改用 Next 能改善整体性能。保留 Nuxt 的理由是已确认的 Vue 组件体系、渲染灵活性和当前 Go 职责划分，而不只是与 nextmoe 相似。依据：[Nuxt 渲染](https://learn.nuxt.com/en/concepts/rendering-modes)、[Next 组件边界](https://nextjs.org/docs/app/getting-started/server-and-client-components)。

建议 account 的登录与授权体验优先 SSR，避免认证瀑布；admin 的交互控制台优先评估 CSR，developer 的公开接入文档可预渲染，私人控制台评估 CSR。最终以首屏、交互、服务器成本和会话安全验证决定，不在本轮创建配置。

静态/CSR 应用可由入口转发 Go 会话接口，不必为代理单独常驻 Node；若使用 Nitro 的服务端能力，则显式计入资源。公开静态资产可缓存，私人响应不可借优化之名进入共享缓存。

Reka 声明支持 SSR，但组合后的焦点和水合仍需实测；Tailwind 在工作区需正确包含共享组件源码，使用静态可发现的类名而非任意字符串拼接。来源：[Reka SSR](https://www.reka-ui.com/docs/guides/server-side-rendering)、[Tailwind 扫描](https://tailwindcss.com/docs/detecting-classes-in-source-files)。

## Go 与协议适配的门槛

chi 使用标准 HTTP handler，Huma 提供验证和中间件能力；项目需避免重复解析与重复验证，但不能因为存在开销而跳过安全检查。协议响应由 Fosite 适配层处理，业务 JSON 由 Huma 处理。来源：[chi](https://github.com/go-chi/chi)、[Huma 验证](https://huma.rocks/features/request-validation/)、[Huma 中间件](https://huma.rocks/features/middleware/)。

Fosite 官方说明生产存储需自行提供，示例内存 store 不能代替持久化设计；其无状态 JWT 校验模式也不提供令牌撤销。选择具体 handler 时只启用项目获准支持的流程，不照搬全部启用示例。来源：[Fosite 官方仓库](https://github.com/ory/fosite)。

保留 Fosite 的前提：能够以可维护的适配实现 Ent 事务、刷新重用、应用配置版本、密钥和标准响应；若只能靠大面积修改上游或绕过存储不变量实现，重新评估协议库或成熟独立授权服务器。该替代仅是失败时评估项，不改动已确认的 Go 架构。

## 缓存与商业依赖

先前文档写 Redis 是候选用途，不是已确认产品。Redis 8 的许可选择与早期发行物不同；Valkey 官方仓库使用 BSD-3-Clause。商业产品要明确采用的版本、发行物和部署方式，不能笼统认定所有兼容服务具有相同条件。来源：[Redis 许可](https://redis.io/de/legal/licenses/)、[Valkey 仓库](https://github.com/valkey-io/valkey)。这不是对具体发行方式的法律结论。

建议优先比较 Valkey 的核心 KV、TTL、原子操作与所选 Go 客户端兼容性；如生产托管资源更适合 Redis，则记录其维护与许可取舍。是否首期必需仍由会话存储、限流、部署实例数和故障语义决定，不只为了“性能”增加依赖。

结合已补充的小规模预期，优先评估 PostgreSQL 持有持久会话/授权状态，单实例内存管理短时限流的最小部署。内存限流重启会丢失且不能跨实例共享，不能用于一次性凭据消费或充当唯一高风险防护；账号失败计数等必要持久约束单独设计。需要多实例或可靠共享短时状态时再引入 KV 服务。该最小部署为建议，不是已确认存储变更，实际查询负载需验证。

权威授权状态和不可丢失事件保留在 PostgreSQL。若会话放在缓存，需要明确驱逐与重启后会话丢失的产品行为；不能把无持久化缓存宣传为可靠业务真源。
