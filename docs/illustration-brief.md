# 看板娘与萌系状态插画需求

日期：2026-10-23。最初为供用户生图的设计建议；用户现已提供两批 12 张场景图并授权接入，实际落点及保留项见文末第 8 节。第 1～7 节保留制作需求作为后续补图与更换素材的依据，不能将其中当时的「待接入」描述当成最新实现状态。

## 1. 使用方法与生成顺序

每张图单独生成、单独导出。建议先完成 **A01 登录迎接、S01 页面迷路、S02 暂无应用、S03 搜索无结果、S04 服务暂不可用**，确认角色与小图画风一致后再做其余素材。首批五张已经能覆盖主要品牌位置与常见状态，不需要一口气生成所有图。

将本文件的「统一角色与画风」和目标素材的「单图描述」一起提交给生图工具，并附用户原来的薄荷绿 C++ 发夹少女参考图。建议各张都使用同一参考图、角色设定及风格描述；不要只靠上一张结果递归生成，以免角色逐渐变化。优先生成 A01 和 S01 作为正常比例、Q 版两条风格的母版。

交付时沿用清单文件名，或同时注明素材编号。文件名不是已经存在的资源路径。**本轮不需要你自行裁剪、压缩、改代码或放进某个目录**，提供原始图片后再统一处理。

## 2. 统一角色与画风

### 已确认的视觉依据

- 唯一角色参考是用户提供的薄荷绿 C++ 发夹少女：薄荷绿短发、雾蓝灰发梢、头顶呆毛、蓝绿眼睛、小方形发夹；白衬衫、薄荷领带、深蓝灰宽松连帽外套、深蓝灰百褶裙、白袜与薄荷配色鞋。站姿全身时保留鞋袜细节。
- 表情温和、有一点安静的程序员气质；可爱、清爽、有亲和力。正常比例沿用参考图的年龄感和身体比例，不擅自增加兽耳、翅膀、长发、泳装或不同制服，不改变角色身份。
- 现有正面立绘只作设定参考，不直接放进产品。新图必须有适合所在场景的动作、视线与构图。
- 组件继续沿用 KunUI 方向的细边框和克制表面，页面组织遵循 nextmoe 对照。插画服务已有布局，不为放图增加巨型卡片、横幅或悬浮角色。

### 画风与配色

正常比例插画用干净的日系动画风，轮廓清楚，柔和赛璐璐阴影，适量发丝与衣褶；不要厚重油画笔触、写实皮肤、3D 塑料质感、强烈镜头光晕或复杂背景。Q 版统一约 2.5～3 头身，保留相同发型、发夹、外套和领带，圆润但不是幼儿化造型。小图应先能读出动作，再考虑衣服细节。

以下是当前项目样式中的品牌参考色，不是要求生图逐像素匹配，也不替代设计系统中的语义色：

| 色彩角色 | 参考值 | 图中用途 |
| --- | --- | --- |
| 薄荷绿 | `#bce4d6` | 头发、领带与少量道具细节 |
| 雾蓝灰 | `#aab9d0` | 发梢、柔和阴影与辅助物件 |
| 深蓝灰 | `#52617c` | 外套、轮廓及道具主体 |

### 所有图共同要求

- **主体和小道具之外透明背景**，PNG RGBA、sRGB。透明区不能画成灰白棋盘格；若工具不能输出真实透明，另交付无纹理纯色底原图并注明，后续再评估抠图，不把白底 JPEG 当透明图。
- 不生成页面 UI、标题、按钮、中文、英文说明、错误码、logo、水印、签名和完整浏览器窗口。包括 404 数字、状态文字都由网页显示，保证四种语言可切换。
- C++ 发夹是角色识别点，保留方形发夹形状与位置；若模型无法稳定生成小字，发夹留白即可，之后再判断是否补字，不在图中堆乱码。
- 单张图只有一个角色；手指和道具关系正确，眼睛与发夹一致，四肢不缺失、不重叠成多余肢体。角色自身服装与参考图一致，不做暴露或性暗示姿势。
- 阴影以角色自身阴影为主；可有很淡、很小的接地阴影，不能留下白色地板、矩形底板、大光斑或覆盖大面积透明区的灰雾。
- 不把文字说明或左右翻转交给图片解决。角色发夹具有方向性，需要不同朝向时单独生成，接入时不直接镜像整张图。
- 首期全部交付静态图，不必做动图、眨眼帧、Live2D 拆层或雪碧图。页面进入动画由前端完成，并尊重减少动态效果设置。

可共用的负面描述：多角色，文字，乱码，水印，签名，网页截图，按钮，复杂背景，白色矩形背景，棋盘格背景，重度光晕，赛博霓虹，写实摄影，3D 渲染，油画厚涂，过度性感，换装，长发，兽耳，多余手指，多余四肢，裁断手脚，模糊轮廓。

## 5. 不需要额外生成插画的位置

- 导航栏按钮、语言切换、分页、文件夹展开、复制、编辑、删除、Toast 和表单校验继续使用统一 SVG 线性图标，不将栅格图片当操作图标。
- OAuth 同意信息区不放大幅角色、不让角色指向「允许」，不覆盖真实应用头像，也不通过表情诱导同意。用户后续要求 OAuth 页面也展示图片，桌面独立品牌区复用迎接插画，授权关系中的 Moetopia 标识使用品牌头像；手机保留小标识、不下载大图。MFA 二维码、恢复码、密码强度和危险操作确认区保持克制。
- 后台首页指标、应用配置详情、审核理由、用户列表及 API 测试响应不在正常有数据时插角色。一个视口尽量只出现一张主要插画。
- 加载中继续使用现有进度条、骨架或 Spinner，不显示「暂无记录」图片；请求失败和真实空结果保持不同状态。
- 不默认给用户站放固定在右下角、持续遮挡页面的悬浮看板娘，不加自动对话、音频或持续摇摆动画。
- 暂不制作维护中专用图：真实维护页面和触发条件尚未确认，可先复用 S04 的视觉而保持具体错误文案准确。

## 6. 后续接入约定

### 当前已有能力与待补能力

当前认证页通过 `packages/portal/app/components/PortalHome.vue` 的 `MoeAuthShell` 品牌插槽组织；A01 应放在该桌面品牌区，保持左侧表单与窄屏行为，不误接到尚未承载这些页面的旧 `MoeAuthLayout` 上。开发者首页需结合实际主视觉容器接入 A02，不重构首页信息层级。

`MoeEmptyState` 已有 `icon` 插槽，但其现有图标区域并不等于完整插画容器。接入状态图时，应在 `@moetopia/ui` 提供统一、可选的插画展示能力并更新 Storybook；不要在各页面复制图片大小、留白和主题处理。无图片、图片加载失败、减少动态效果等状态也要保留完整文字和操作。

整页 404/403/服务错误需要适配两个 Nuxt 应用的实际错误处理；本轮仅规划素材，不声称新错误页面已实现。仅在正确的状态分支加载对应资源，不用装饰图替代错误判定、重试、返回和重新登录操作。

### 资源与可访问性

- 本清单建议后续将可复用发布资源统一维护于 `packages/ui/src/assets/illustrations/`；该目录与新资源本轮不创建，实际接入时确定导入与构建方式。页面通过共享 UI 使用，不在两个应用各复制一份图片。
- 接入前核对画面比例、真实 alpha、边缘白边、角色一致性、小尺寸辨识，以及明暗背景效果。保留原始 PNG，发布衍生图减少尺寸和字节数；不把生成原图无差别打入所有路由。
- 宽高与容器比例显式声明，预留布局空间；首屏以下按需加载。A01 单张发布资源建议以 250 KiB 内为优化目标，状态小图以 80 KiB 内为目标，画质与实际尺寸一起评估，不为凑数破坏轮廓。
- 文字已描述状态时，插画作为装饰使用空 alt；独立承担含义的图才提供对应四语替代文本。错误码、标题与按钮永远是真实 DOM 文本，不烘焙进图片。
- 提交图片时如有版本差异，可用 `A01-v1`、`A01-v2` 命名；接入记录注明最终使用版本。角色名称、作者/生成来源和可使用范围以用户实际提供信息记录，不虚构素材授权声明。
