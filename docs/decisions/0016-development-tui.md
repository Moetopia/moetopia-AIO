# ADR-0016：开发服务的独立终端输出

2026-10-18 更新：前端数量、目录和默认启动列表已由 [ADR-0017](0017-user-site-layouts.md) 替代，当前为 account 用户站（含 developer）＋独立 admin；以下保留当时的工程或验证记录。

日期：2026-10-18。状态：根据用户要求完成开发启动器调整；Windows 实测通过，Linux/macOS 生命周期未实测。

## 问题与方案

旧启动器让四个服务继承同一个输出，日志交错；任一服务退出就停止全部服务，难以判断故障来源。采用锁定的开发依赖 mprocs 0.9.6 管理终端视图，保留项目已有的 Go 重建和各应用原始 dev 命令。

`pnpm dev` 在交互终端使用每服务独立输出、运行状态和单独重启；非交互终端自动切换带服务名前缀的纯文本输出，另提供 `pnpm dev:plain`。支持显式选择 api/account/admin/developer/storybook；默认仍为 API 和三个应用。命令和键位以 [开发预览](../live-development.md) 为唯一操作说明。

## 进程与配置边界

- 项目先加载既有 .env，再按所选服务检查端口；服务重启也检查，不能复用归属不明的监听者。
- 使用命令参数数组传递 Node/pnpm 绝对路径，保留 Windows 独立 pnpm.exe 与含空格路径支持，不拼接 shell 命令。
- 每次生成独立的 `.data/dev/mprocs-<pid>.yaml`，仅含命令路径和界面配置，不序列化环境变量或凭据；退出删除。日志不落盘，回滚行数有限。
- Windows 使用终端 Ctrl-C 触发服务包装层，清理该包装层启动的子进程树；TUI 的普通停止/重启/退出均使用这一操作。应用失败不会自动停止其他服务，也不无限自动重启。
- 不新增后台 daemon，不控制 Ubuntu Docker 或改变已有依赖部署。UP 仅代表进程仍在，不替代 readyz 或编译/业务验收。

## 验证与维护

`pnpm test:dev` 通过，覆盖服务筛选、错误服务名、端口冲突不干扰原监听者、Node/pnpm 参数边界和带空格路径。

Windows 真实 TUI 验证四个服务同时启动，API readyz 和三个页面均返回 200；停止 account 后其他三个继续返回 200，重启 account 后恢复 200；退出后四个本轮测试端口均释放。另用独立 API 端口验证 TUI 单服务启动/重启，以及纯文本 Ctrl-C 清理。测试未改变 .env 或停止已有开发进程，不等于重新完成身份业务浏览器验收。

升级 mprocs 或改换终端管理器时重测 Windows 信号、重启与子进程清理，锁文件随依赖变更维护。版本依据：[mprocs v0.9.6 官方说明](https://github.com/pvolok/mprocs/blob/v0.9.6/README.md)。当前只新增该开发依赖，未改业务依赖版本。
