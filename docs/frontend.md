# 前端工程规范

状态：Nuxt + Vue + TypeScript；用户最新授权采用 account 用户站（含 developer）＋独立 admin，见 [ADR-0017](decisions/0017-user-site-layouts.md)。已有账号与授权流程不等于全部业务已完成；实际完成边界见 [实施进度](implementation-status.md)。

通用命名、类型、格式和“默认不添加注释”规则见 [代码规范](coding-standards.md)。本文件仅补充前端职责，不另设注释例外。

## 应用与共享边界

account 用户站包含认证、账号中心和 `/developer` 分区；admin 独立管理平台。用户站按路由与 Nuxt layout 区分认证、账号页和开发者控制台，不因同源就混合领域状态。两应用共享 `@moetopia/ui`、公共翻译和生成的业务 API 类型，不互相导入源码；账号业务组件不因为多处“长得相似”就进入基础 UI 包。

Nuxt 服务端负责渲染和必要转发，身份校验、签发、授权及业务写入归 Go。Go 统一管理会话已确认，具体代理与 Cookie 设计见 ADR-0006；不得让 middleware 中一个布尔值变成第二套权威登录状态。

2026-10-19 用户要求用户中心和开发者中心也通过 OAuth/OIDC 登录，见 [ADR-0019](decisions/0019-first-party-oidc.md)。已接 Go RP 契约：普通页面读取 portal/context，密码/注册/授权使用 account/context，二者不能互相充当登录证据。身份认证页不受 RP 登录守卫保护；登录启动使用顶层导航，不能用 fetch 跟随重定向。前端不截获回调或保存令牌。

## 页面与组件

- `app/pages/` 负责路由、页面元信息和单个页面容器；复杂请求与交互进入对应功能目录。
- 业务容器建议放 `app/components/<feature>/`，可复用逻辑放 `app/composables/`，纯工具放 `app/utils/`。
- 服务端和客户端可共享的安全纯类型/工具放 `shared/`；秘密、数据库访问和 Node 专属代码不能进入共享包。
- 常量按功能归属保存；跨应用的 API 类型从生成包导入，不手写相同 DTO。领域展示类型与传输 DTO 分开。
- Vue 使用 Composition API 与 `script setup`；自定义前端函数默认箭头函数，不修改上游或生成代码以满足风格。
- 避免目录名和组件名重复造成 Nuxt 自动导入歧义；共享包使用显式公开导出，不依赖应用的自动导入。
- 路由页面及过渡容器保持一个真实根元素；不以 `display: contents` 代替过渡宿主。具体 Nuxt 版本行为需验证。

文件拆分按职责和可读性，不规定所有页面必须复制固定层数。

### 可复用界面的归属

**凡是具有复用价值的视觉结构或交互组件，都应优先复用 `@moetopia/ui`；现有组件不能满足时，直接在 `packages/ui` 中新增或完善，再由应用通过公开入口使用。不得在不同页面或应用中复制相同的模板、控件样式和交互实现。** 该规则适用于基础控件，也适用于页框、顶栏、侧栏、插画布局、页面标题、设置行、信息列表、加载、错误和空状态等组合组件。

- 编写页面前先检查 UI 库；识别到复用价值时，在首次实现中提取共享组件，不以“先在页面复制、以后再整理”为默认做法。
- 共享视觉通过有明确语义的 props、slots 和 emits 组合，消费统一设计变量；新增组件同时提供 Storybook 示例及与交互风险相称的验证。
- UI 库保持纯展示与通用交互，不依赖 Nuxt 路由、登录态、业务 API、权限规则或特定业务模型；应用通过插槽和适配传入内容及操作。
- 请求、授权判断、业务校验和领域状态仍归应用的功能组件或 composable；多个 Nuxt 应用的 Cookie、运行时配置等框架适配可放共享 portal 层，但不得在那里另建一套视觉组件库。
- 一次性业务内容可以组合共享组件；只因布局相似而业务职责不同，不强行合并成大量布尔参数控制的万能组件。
- 修改共用组件时同步现有消费者，评审同时检查重复模板/样式是否遗漏提取；不允许通过复制改名绕过本规则。

### 参考布局的实现与验收

用户要求 nextmoe 的布局和交互尽量 1:1。实施前定位具体参考源文件，核对容器宽度、栏宽、间距、断点、粘滞行为、菜单位置和操作次序；不得只保留抽象“顶栏/侧栏”后自行换成通用后台。基础控件沿用 KunUI 方向与 Moetopia 品牌变量。应用特有内容与未实现后端能力明确列出差异；不能假造数据、可用按钮或授权成功。几何测试、截图与业务验证分别记录，不宣称用户已经验收。当前对照见 [布局核对](ui-layout-audit.md)。

完整页面与交互清单见 [nextmoe 对照](nextmoe-parity.md)。每轮主动检查可接接口与同范围页面，集中完成导航、表单、弹窗、反馈和跳转；不能只做用户当轮指出的单个外观问题。缺少服务端能力时仍补足能安全评审的 UI，并集中记录后端契约，最终提交禁用且解释原因，不能捏造成功。

## 请求、状态与缓存

- 优先 Nuxt 的 SSR 数据能力，正确区分首次 SSR 请求、客户端刷新及交互提交，防止同一次渲染重复请求。
- 组件局部状态使用局部响应式变量；URL 保存可分享的筛选与分页；跨页面用户体验状态才考虑 Pinia。Pinia 本身未定为必要依赖。
- 用户上下文按请求隔离，不在模块顶层创建全局可变登录用户；SSR 不读取浏览器专属 API。
- API 类型来自 OpenAPI，但运行时仍依赖服务端校验。不要对非空断言、`any` 或默认空对象产生的“成功”状态放行。
- 可选分页和搜索参数没有值时省略，不发送空字符串占位；首页不携带 cursor/after，清空筛选也移除 query。验证应包含真实接口，不能只依赖忽略查询参数的页面 mock。
- 区分初始加载、无数据、错误、成功和后台刷新；取消过时请求，避免搜索或路由切换导致旧响应覆盖新数据。
- 401 进入可恢复的登录流程；403 展示权限不足，不反复刷新；429 尊重重试提示；5xx 保留用户输入并允许重试。
- 写请求不自动重试，除非有明确幂等契约。会话失效不以假数据维持已登录界面。
- 私人页面和身份接口禁止 CDN/共享缓存；SSR payload、错误对象和客户端状态均不包含秘密或服务端令牌。

统一错误语义见 [API 契约](api-contracts.md)，不要让每个页面自创字段和错误映射。

## 表单与身份交互

客户端校验用于及时反馈，Go 校验是权威。每个字段有标签、说明和关联错误，提交失败聚焦合适位置。支持密码管理器、合适的 autocomplete、粘贴和可访问的显示密码按钮。

密码、验证码和恢复码不持久化到浏览器存储。提交后保留必要非敏感输入，禁止重复提交；错误不暴露账号存在性。回跳参数只通过受验证的授权事务继续，不让页面直接信任任意 redirect URL。

文档在线测试只为显式调试使用局部内存，不成为用户站登录或令牌管理实现。仅 Public 协议测试与受控业务请求可在页面运行；不收集 Confidential secret，不借用独立管理员 Cookie。输入/响应在离开、切换和清空时销毁，写入不重试；完整边界见 [站内开发者文档](developer-documentation.md)。

用户取消授权、第三方拒绝、过期会话和网络中断分别给出可操作说明。暂存的审核配置不渲染为已生效配置。

## 国际化与视觉

当前前端提供简体中文、繁体中文、英文和日文。翻译按语言独立保存于 `packages/locales/src/lang/zh-CN.ts`、`zh-TW.ts`、`en.ts`、`ja.ts`，各文件内按 common/account/portal/authorization 分组；不得再将所有语言堆进按功能分组的大文件。`types.ts` 与注册表检查键结构，新增语言必须完整填写消息并注册原生语言名，不以英语对象展开冒充完整翻译。

语言菜单消费统一注册表并显示当前选中项，不在页面硬编码二选一开关。无效 Cookie 在 SSR 与客户端都回退简体中文；切换不刷新页面、不丢表单。页面、表单、验证和授权说明纳入翻译；日志、协议错误码和 scope 原文不做语言化标识。邮件接口目前只接受 zh-CN/en：前端繁中映射 zh-CN、日文映射 en，由 emailLocale 适配，不擅自修改 Go 契约或宣称邮件已有四种翻译。

新增语言还应验证键完整性、母语名称、日期、长标签、窄屏、刷新持久化与邮件参数。动态消息使用完整句子，避免将语序不同的语言拼接成句。默认简体中文，用户选择优先于推断；主题仍按已实现偏好处理，不借本轮语言改造增加其他状态管理库。

建议默认简体中文，用户选择优先于浏览器推断；服务端渲染与客户端读取相同语言来源。主题以明确用户选择为先，缺省跟随系统，避免水合后闪烁。语言与主题优先级是建议，需实际验证。

视觉规范统一见 [design-system.md](design-system.md)。页面不硬编码控件色值、不复制弹窗实现；图表等确需固定语义颜色时在设计变量层定义。

页面与布局转场由共享 Nuxt 层统一设置，视觉定义在 UI 的 experience.css。页面保持单个真实根元素，out-in 过渡期间不同时保留两套可操作身份表单。导航进度由 useLoadingIndicator 的页面生命周期驱动，UI 仅展示；完成、错误与卸载都必须结束，不使用独立的假进度定时器，系统减少动态效果时取消位移。具体对照及保留差异见 [布局复核](ui-layout-audit.md)。

## 服务端转发

固定上游地址和允许路径，不提供任意 URL 代理。只信任配置内入口的转发头，正确保留所需多条 Set-Cookie；不向其他 origin 转发浏览器所有 Cookie。错误、超时及上游状态不转换为 HTTP 200。

Cookie 来源和处理责任以 ADR-0006 为准；不能因为浏览器“拿不到 Cookie”改成 localStorage 存刷新令牌。

## 前端验收

检查 SSR 用户隔离、直接进入私人页面、登录过期、移动布局、中英文、明暗切换、键盘、刷新/返回导航和慢网络。组件故事与端到端用例职责见 [测试发布](testing-release.md)。

当前用户站页面壳使用 SSR，RP 状态挂载后由 Go portal/context 读取，私人身份不进入 SSR payload；admin 为静态 CSR。账号/开发者共享应用级 RP 上下文；身份认证上下文独立、按认证路由读取。401 清除旧 RP 展示，依赖失败保留重试状态而非自动登录循环；会话撤销/本地退出使用 portal CSRF，不结束中央身份。切换 layout 不伪造管理员身份。公开接入文档预渲染尚未实现。Go 仍拥有会话，私人响应不进入共享缓存。首屏和资源预算仍需按 [性能规范](performance.md) 实测，不能用构建通过代替。
