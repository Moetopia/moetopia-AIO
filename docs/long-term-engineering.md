# 长期工程与商业化选型原则

状态：长期、专业化、工程化、面向商业项目的判断尺度由用户明确提出；下述检查方法为本项目工程基线。本轮仅维护文档，不开始实施。

## 目标

优化多年演进期间的正确性、可维护性、发布与恢复能力及总拥有成本。首期开发速度可以比较，但不能作为选型的主要理由；熟悉参考项目也不能代替对适配性和长期成本的判断。

专业化不等于预建全部企业功能。多租户、微服务、组织与计费仍遵守产品已确认范围；没有需求时保留边界，不提前引入实现复杂度。

当前用户预期活跃规模最多双位数。长期工程要求主要体现为清楚的边界、正确的身份协议、可审查迁移、可恢复发布和持续维护；运行架构优先保持低资源、低运维成本。用户数少不取消安全要求，也不要求以大流量平台的运行规模起步。

## 依赖选择的必要证据

| 维度 | 需要回答的问题 |
| --- | --- |
| 正确性 | 能否表达事务、并发条件、权限和数据约束，怎样验证失败场景？ |
| 演进 | 字段、模型与接口变更是否可发现、可审查、可分阶段发布？ |
| 模块边界 | 依赖会否渗透所有用例，替换或拆分是否必须重写业务？ |
| 运维 | 是否支持可观测、备份恢复、密钥轮换、迁移锁与故障诊断？ |
| 维护 | 上游治理、发布记录、安全响应、版本兼容与升级成本是否明确？ |
| 商业使用 | 实际采用的发行物、插件及传递依赖有哪些许可、付费和账号要求？ |
| 可重复 | 生成、构建、测试与迁移能否在固定版本和干净环境复现？ |
| 团队成本 | 新维护者能否理解系统，规范能否通过工具和测试落实？ |
| 退出路径 | 数据、schema 和契约是否独立于供应商，如何替换关键依赖？ |
| 性能与容量 | 关键用户路径的尾延迟、资源上界、并发正确性及扩容成本是否可测？ |

不以 star 数、单次跑分、项目名气或“企业级”宣传词替代上述证据。维护状态核对需要实际发布日期和安全渠道；本轮未完成的审计明确留待验证。

## 数据与 ORM 的长期要求

ORM 选择与迁移执行器分别决策。显式模型和生成类型有助于发现错误，但不是自动安全保证；版本迁移、数据库约束、并发测试和发布顺序不可省略。

持久化实体限制在模块适配层，不把全系统织成可任意遍历的关联图。退出 ORM 时可保留 PostgreSQL 数据、SQL 迁移历史和业务 API，主要重写适配层，而不是承诺替换零成本。

如果候选的关键能力依赖付费产品，应说明用到哪项能力、许可与预算影响，以及自维护或替代路径。付费工具可作为明确预算决策，不能隐式成为构建或发布必需项。

## 接口、安全与发布

协议接口优先标准互操作，业务接口有版本、错误语义和兼容策略。安全凭据分类管理，JWT 并不免除状态与撤销设计。运营开关、应用配置版本及管理操作需要审计和故障恢复。

发布必须能够说明旧应用与新 schema 的兼容、迁移顺序、回滚限制和恢复步骤；不能用“自动迁移”或“重启即可”替代设计。备份应通过恢复演练验证。

SLO、容量、数据保留、值守与事件响应预算在上线前明确；本轮不虚构商业 SLA。可观测和运行文档是交付的一部分，不等生产故障后才补。

## 本轮对选型的影响

- Ent + 独立 SQL 版本迁移已确认为文档基线；同时审查代码生成、迁移许可和模块隔离成本，见 [ADR-0010](decisions/0010-orm-comparison.md)。
- 对外令牌倾向 JWT，但建议非对称签名、公钥分发、标准 claims 和分级撤销校验，见 [ADR-0012](decisions/0012-access-token-profile.md)。
- 原型验证将来作为选型门槛，而非本轮实施内容；验证不通过需重新比较，不能为了保持先前结论隐瞒成本。
- 所有框架统一复核，结论和限制见 [stack-review.md](stack-review.md)；性能测量、容量预算和验收见 [performance.md](performance.md)。
